# Methodology

## 4.1 Research Design

The dissertation adopts a mixed-methods design [@creswell2023research], combining controlled empirical experimentation with analytical modelling. The empirical strand addresses the questions concerned with measured outcomes, namely the contribution of individual tuning interventions (RQ1), the effect of PTP hardware timestamping on measurement uncertainty (RQ2), and the residual gap against kernel-bypass baselines (RQ4). The analytical strand addresses RQ3, which asks whether a formal scheduling-latency bound can predict the observed 99.9th-percentile latency. The two strands are deliberately cross-validated: empirical observation disciplines the assumptions of the model, and the model in turn establishes the prior expectation against which the measurements are judged. This reciprocal structure is what allows the study to report percentiles as tests of a theory rather than as isolated numbers.

## 4.2 Experimental Platform

Experiments are conducted on Amazon EC2 c7i.metal instances, which expose the Nitro PTP Hardware Clock through the /dev/ptp0 device and support hardware packet timestamping on the Elastic Network Adapter [@aws2024timesync; @aws2024flowtraders]. Bare-metal instances are chosen so that measurements are not perturbed by a co-resident hypervisor scheduler, while retaining the public-cloud setting in which the research gap was identified. Instances are deployed within a single cluster placement group in one Availability Zone, which minimises network-path variability between the producer and consumer hosts. The operating system is Ubuntu 24.04 LTS running a long-term-support kernel in the 6.8 series, optionally patched with PREEMPT_RT for the fully tuned scenario. The decision to use cloud infrastructure rather than dedicated hardware is a deliberate part of the contribution: it broadens the applicability of the findings, lowers the barrier to replication, and targets the virtualised regime that the literature has left uncharacterised.

## 4.3 Workload and Instrumentation

A synthetic HFT tick-to-trade workload is implemented in C++20. It comprises three pipeline stages, a market-data producer, a strategy evaluator, and an order emitter, connected by single-producer single-consumer lock-free ring buffers. Messages follow a Poisson arrival process at four offered loads of roughly 100,000, 300,000, 1,000,000, and 3,000,000 messages per second, which approximate equity-market feed rates during active trading. The Poisson model is chosen because it makes the queueing behaviour near saturation analytically tractable, so that the tail growth observed empirically can be compared against a theoretically motivated expectation.

Hardware timestamps are captured at four points along the pipeline: NIC ingress through ENA hardware timestamping, application read, post-strategy decision, and NIC egress. This four-point decomposition mirrors the tick-to-trade breakdown used by practitioners while remaining fully reproducible without vendor-specific hardware. Latency samples are accumulated in HdrHistogram structures [@tene2014hdrhistogram], which preserve the full distribution at constant memory cost and allow high percentiles to be recovered accurately, a property that ordinary summary statistics do not provide for heavy-tailed data.

## 4.4 System Architecture and CPU Layout

The experimental topology consists of two instances, a producer and a consumer, each equipped with the Elastic Network Adapter and the PTP Hardware Clock, with a common time reference supplied by the GPS-disciplined Amazon Time Sync infrastructure. Data-plane traffic flows between the two instances while PTP synchronisation runs on a separate logical path, so that the measurement clock is decoupled from the system under test.

Under the fully optimised configuration the CPU, IRQ, and NUMA resources are partitioned explicitly. Network-interface interrupts are pinned to a pair of cores on NUMA node 0. Two cores are reserved for housekeeping work so that kernel background activity does not contend with the critical path. The ring-buffer producer runs on a dedicated pair of cores, and the strategy evaluator runs on a further set of cores on the same NUMA node under the SCHED_FIFO real-time policy. Keeping the producer, the evaluator, and the interrupt handlers on a single NUMA node avoids cross-node memory traffic, which Section 2.2 identified as a dominant source of variance.

## 4.5 Experimental Scenarios

Six configurations form a gradient of increasing intervention, which permits the contribution of each mechanism to be attributed rather than confounded. Scenario S0 is stock Ubuntu with the default irqbalance daemon. Scenario S1 adds IRQ affinity, pinning interrupts to NUMA-local cores. Scenario S2 adds CPU isolation through the cgroup v2 cpuset controller. Scenario S3 adds NUMA-aware memory allocation. Scenario S4 adds nohz_full tickless operation on the isolated cores. Scenario S5 adds PREEMPT_RT with the strategy thread running under SCHED_FIFO. Each scenario is a strict superset of the previous one, so the difference in measured latency between consecutive scenarios isolates the marginal effect of the single mechanism that was added.

Each scenario runs at each of the four offered loads for 30 minutes, following a five-minute warm-up that is discarded. Ten independent trials are conducted per cell on freshly provisioned instances. Fresh instances per trial guard against state accumulated across runs and against a single unlucky instance placement dominating the result, and the replication supports the inferential statistics described in Section 4.7.

## 4.6 Analytical Scheduling-Latency Model

The analytical component instantiates the scheduling-latency bound derived for PREEMPT_RT by Bristot de Oliveira and colleagues [@bristot2020demystifying]. Their result expresses the worst-case scheduling latency as the sum of a set of blocking and interference terms: the sched-tail delay, the longest preemption or interrupt-disabled interval that postpones the scheduler, the transient preemption and interrupt-enabled window preceding a scheduler invocation, the duration of the scheduler's own code path, and two load-dependent interference functions arising from non-maskable and ordinary interrupts. Because the interference terms themselves depend on the latency being bounded, the expression is evaluated iteratively until it converges to a fixed point.

In this work the interference functions are not taken from the literature but parameterised directly from per-scenario interrupt rates measured on the running system through the kernel osnoise tracer. This yields a predicted 99.9th-percentile bound for each scenario, which can be compared against the empirically measured percentile. Because arrivals are Poisson, the model is evaluated at each of the four loads in order to test whether it captures the super-linear growth of the tail as the system approaches saturation. The comparison of prediction against measurement constitutes the falsifiable test at the centre of RQ3.

## 4.7 Metrics and Statistical Analysis

The primary metrics are the 50th, 95th, 99th, and 99.9th percentiles of tick-to-trade latency, recovered from the per-trial HdrHistogram accumulators. Secondary metrics include per-core interrupt counts, context-switch rates, cache-miss counts read from hardware performance counters, and the PTP offset reported by phc2sys, which together allow an observed change in latency to be attributed to a plausible mechanism rather than merely recorded.

Because latency distributions are heavy-tailed and far from Gaussian, distributional differences between scenarios are assessed with the two-sample Kolmogorov-Smirnov test at a significance level of 0.01, with a Bonferroni correction applied across the family of pairwise comparisons. Confidence intervals for the tail percentiles are obtained by the non-parametric bootstrap with ten thousand resamples, which makes no distributional assumption. Effect sizes are reported as Cliff's delta [@cliff1993dominance], a non-parametric measure appropriate for ordinal, non-normal data without an equal-variance assumption. Reporting an effect size alongside the significance test ensures that a difference is shown to be not only statistically detectable but also of a magnitude that matters in practice.

## 4.8 Ethical and Professional Considerations

Because the workload is entirely synthetic and no live market data, real order entry, or exchange connection is involved, the research carries no risk of market impact or regulatory breach, and no human subjects are implicated. Two secondary considerations are addressed explicitly. First, cloud experimentation incurs a non-trivial energy cost; the number of trials is fixed in advance by an a priori power analysis so that no more compute hours are consumed than are needed to detect the target effect size. Second, the data, source code, and configuration artefacts are released under the permissive Apache 2.0 licence with documentation sufficient for independent replication, consistent with reproducibility norms in systems research [@creswell2023research]. The choice of AWS is justified by current PTP Hardware Clock availability; the methodology itself is vendor-agnostic and portable to equivalent offerings as they become generally available.
