# 7 Discussion

## 7.1 Interpretation of Findings

On this platform the untuned tail is caused mainly by scheduling. Under SCHED_OTHER the measured thread competes with the load on equal terms and, under contention heavy enough to keep the load average above the number of hardware threads, occasionally waits milliseconds for the running task to reach a preemption point. SCHED_FIFO removes that competition because a runnable real-time thread preempts every SCHED_OTHER task at once. The remaining tail, tens to a few hundred microseconds, is what the scheduler cannot remove: non-preemptible kernel sections, interrupt handling, and interference through shared hardware. This matches the decomposition of @bristot2020demystifying, in which the latency of the highest-priority thread is bounded by blocking from non-preemptible sections and interference from interrupts; on a non-real-time kernel those sections are longer and unbounded, which is why PREEMPT_RT is still needed to bound the worst case rather than the 99.9th percentile. It also explains why the priority value made little difference: the picks in Table 6.2 span priorities 1 to 99 with tails in the same range, because the measured thread was the only real-time thread of the workload.

The adverse effect of isolation needs the most explanation. Practitioner guides treat core isolation as one of the first steps in latency tuning [@databento2024lowlatency], but they mean isolation at boot combined with measures that keep the core out of idle states. Isolation by affinity achieves only the first half. Once the load is removed the core has nothing to do between wake-ups, so it enters an idle state and pays the exit latency on the next wake-up; @schoene2015wakeup showed that these latencies range from microseconds for shallow states to hundreds of microseconds for deep ones. Here the entries were mostly to the shallow C1E and C3 states, but they occurred after almost every wake-up, so even exit latencies of tens of microseconds reached the 99th percentile, and a busy loop that kept the core awake without competing with the measured thread removed the penalty. Isolation is therefore not harmful in itself: it moves the bottleneck from the scheduler to power management, and only a configuration that addresses both delivers the expected benefit. The SMT result fits the same picture. A compute-heavy worker on the sibling slows the measured thread through shared execution units and caches [@tullsen1995smt], and removing it reduced the 99.9th percentile by 45 per cent, an effect no scheduler setting can produce. But a physical core can only enter its deeper idle states when both hardware threads are idle, so freeing the sibling also removed the protection a loaded sibling had provided, and the 99th percentile rose under SCHED_FIFO. Freeing the sibling trades a better extreme tail for a worse 99th percentile unless idle states are controlled. This also reconciles the simulation, whose model was calibrated to a literature that describes boot-time isolation with idle-state control, with the real result: the follow-up shows that this is the form of isolation that helps.

The real search comparison and the simulation agree once the structure of the two spaces is considered. In the real space one binary parameter accounts for almost all the variation, and a search that samples each parameter independently sets it favourably half the time, so a random sample of 10 configurations contains a SCHED_FIFO configuration with probability $1 - 2^{-10}$, and any SCHED_FIFO configuration already satisfies H1. The remaining differences among SCHED_FIFO configurations, from about 11 to 124 microseconds in a single run, are of the same order as the run-to-run variation of one configuration, which is why five seeds could not separate the methods. The simulation shows the same pattern at larger scale: random search reliably samples the dominant parameter but leaves a median regret of 5 to 15 per cent because it does not refine the remaining parameters. The practical advantage of Bayesian optimisation on the real host lay in how the budget was spent: 15 per cent of its measurements after initialisation went to SCHED_OTHER configurations, against 57 per cent for random search. When each measurement costs minutes of machine time or hours of cloud instance time, that economy is the main benefit, which agrees with the observation from CherryPick that the value of model-based search lies in the expensive evaluations it saves [@alipourfard2017cherrypick] and with @bergstra2012random on the competitiveness of random search when few parameters matter.

Re-measurement changed the picture as the early 20,000-sample simulation had suggested it would: the best observed medians of 11 and 15 microseconds became re-measured medians of 19 and 61. A search that reports its best observed value reports partly the luckiest measurement, a winner's-curse effect that grows with the number of measurements, and studies that report only the best configuration found should be read with that in mind. A tuning procedure should always end by re-measuring its choice.

## 7.2 Implications for Practice

Four recommendations follow. Run the latency-critical thread under a real-time scheduling class; on this machine that one change removed about 97 per cent of the 99.9th-percentile latency and needs only a raised RLIMIT_RTPRIO, not root. Do not isolate a core by affinity alone; either keep it out of idle states, through the power-management latency target or a busy-polling design, or leave it shared. Keep the SMT sibling of the critical core free of heavy work, together with idle-state control. When tuning automatically, prefer a model-based search for its economy of measurements and always re-measure the selected configuration. The regulatory dimension is only partly addressed: RTS 25 constrains timestamp accuracy, not latency [@ec2017rts25], and this study made no PTP measurement. It does show that on an untuned host a single wake-up can be delayed by more than 20 milliseconds under load, so any software timestamp taken by such a thread can err by far more than the 100-microsecond tolerance. Tuning kept the worst case below one millisecond in 40 of the 50 re-measurement runs, but one run still contained a wake-up above 20 milliseconds; bounding the tail is necessary for credible software timestamping but not sufficient.

## 7.3 Limitations

Six limitations bound these conclusions. The metric is scheduling latency, a component of tick-to-trade latency but not the whole of it. The study used one workstation, one processor model, and a generic kernel; idle-state latencies, SMT behaviour, and interrupt routing differ between processors, so the magnitudes do not transfer directly to servers or cloud instances, although the direction of the main effects is more likely to. The experiment ran without root, so the power-management latency target, IRQ affinity, isolcpus, nohz_full, and PREEMPT_RT were unavailable and isolation was approximated through the affinity of the load. The contention was synthetic and heavier and more uniform than that of a production host, so the measured effects are probably larger than production would show. Five seeds per method were enough to show that both methods meet the success criterion but not to establish a significant difference between them. And the simulation's latency model was calibrated by hand, and its sensitivity study tested only one-at-a-time perturbations. Each limitation is addressed by an item of future work in Section 8.3.
